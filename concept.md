# Концепция планировщика отчетности «Финалогика»

Дата: 13 октября 2026 года.

Документ описывает будущий проект по ответам заказчика и приложенному брендбуку. Код страницы пока не создается. Рабочее название: «Финалогика · Планировщик отчетности».

## 1. Задача проекта

Создать удобный планировщик для руководителя и 20 сотрудников бухгалтерской компании. На одном экране должно быть видно, по какому клиенту, какой отчет или платеж, к какому сроку и у какого сотрудника запланирован, а также что уже отправлено, сдано или принято.

Основные сценарии:

- Руководитель выбирает всех сотрудников и контролирует общий план и просрочки.
- Сотрудник выбирает себя и видит свои задачи по закрепленным клиентам.
- Руководитель один раз настраивает правила сроков и набор обязательств клиента. Задачи на следующие периоды создаются автоматически.
- Сотрудник меняет статус и при необходимости оставляет комментарий. В совместной версии результат видят другие пользователи с соответствующими правами.

Интерфейс рассчитан на компьютеры. Основной формат работы — таблица с закрепленной слева колонкой клиентов, а не календарная сетка.

## 2. Хранение и совместная работа

### Исходное ограничение

Три файла HTML, CSS и JS с хранением только в localStorage подходят для локального прототипа. localStorage хранит данные в конкретном браузере и не синхронизирует их между компьютерами. Даже открытие одной страницы по общей ссылке или из сетевой папки не создает общего хранилища.

Поэтому одновременно обеспечить «только localStorage, без серверов и баз данных» и «изменения автоматически видны 20 сотрудникам на разных компьютерах» невозможно. Это техническое противоречие требований, которое нужно разрешить до реализации совместной версии.

### Предлагаемое решение

Сохранить интерфейс на обычных HTML, CSS и JS. Для реальной работы команды подключить единое хранилище с авторизацией и передачей обновлений в открытые страницы сотрудников. LocalStorage использовать только для личных настроек интерфейса, например выбранного периода и фильтров.

Пример подходящей архитектуры: веб-страница → сервис доступа к данным → общее хранилище → обновления в браузерах сотрудников. Сервис может размещаться у компании или у выбранного поставщика. Один из технических вариантов — платформа с готовыми авторизацией, базой и обновлениями, например Supabase; конкретный поставщик и размещение пока не выбраны.

Для командной версии предусмотреть:

- Индивидуальный вход сотрудников и отдельные права руководителя.
- Проверку прав на стороне общего сервиса. Выбор имени в выпадающем списке сам по себе не защищает данные.
- Автоматическое обновление открытых страниц после сохранения изменений.
- Показ состояния «Сохранено», «Сохраняется», «Нет соединения».
- Повторную загрузку актуальных данных после восстановления соединения.
- Защиту от незаметной перезаписи, если два человека одновременно редактируют одну задачу.
- Историю изменения статусов: кто, когда и что изменил.
- Резервное копирование общих данных и возможность выгрузки.

При отсутствии соединения командная версия не должна показывать несохраненное изменение как успешно сохраненное. Полноценную работу без интернета с последующим объединением правок в первую версию не включаем.

### Этапы

1. Локальный прототип: три файла `index.html`, `styles.css`, `app.js`, демонстрационные данные и localStorage. Он проверяет таблицу, сроки и удобство работы. Совместной синхронизации в нем нет.
2. Командная версия: тот же интерфейс с общим хранилищем, входом сотрудников и синхронизацией. Ограничение «без серверов и баз данных» для этого этапа потребуется снять.

Это предложение по архитектуре, а не уже согласованная замена исходного требования. Создание сервисов, учетных записей и публикация не входят в текущий этап подготовки концепции.

## 3. Сотрудники, клиенты и ответственность

У клиента достаточно хранить наименование. Внутренний уникальный идентификатор позволит различать записи даже при одинаковых названиях.

У одного клиента могут быть разные ответственные:

- Главбух отвечает за выбранные бухгалтерские и налоговые отчеты.
- Зарплатник отвечает за выбранные зарплатные отчеты.

Ответственного назначаем каждому обязательству клиента. Общая связь «клиент — сотрудник» не должна автоматически назначать все отчеты одному человеку.

Пример: у ООО «Вектор» НДС ведет Анна, а РСВ и 6-НДФЛ — Мария. При выборе Анны отображаются ее задачи по «Вектору», при выборе Марии — ее задачи, при выборе всех — оба набора с указанием исполнителя.

Одна задача имеет одного основного ответственного. Если для одного отчета нужна совместная работа нескольких исполнителей, это отдельное расширение.

В локальном прототипе выбор сотрудника — фильтр, доступен режим «Все сотрудники». В командной версии предлагается: сотрудник видит свои задачи, руководитель — всех и каждого отдельно. Права на просмотр чужих задач сотрудниками требуют отдельного решения.

## 4. Справочники

Разделы: «Сотрудники», «Клиенты», «Отчеты и платежи».

Начальный список видов обязательств:

НДС, Налог на прибыль, Налог на имущество, Транспортный налог, РСВ, 6-НДФЛ, ЕФС-1, Перс. сведения, УСН, Патент.

Список редактируемый: можно добавлять виды, менять названия и архивировать неиспользуемые записи. Архивирование сохраняет историю задач.

Сдача отчета и уплата налога — отдельные задачи с разными сроками и результатами. Например, назначение НДС может включать задачу сдачи и отдельные задачи уплаты. Нельзя считать платеж выполненным только потому, что отчет сдан.

Каждый шаблон содержит:

- Название и тип: сдача отчета или уплата.
- Категорию ответственности: главбух или зарплатник, с возможностью назначить конкретного человека у клиента.
- Периодичность: ежемесячно, ежеквартально, ежегодно либо индивидуальный график.
- Правило определения отчетного периода.
- Правило срока: день и месяц относительно периода либо список дат.
- При необходимости отдельное правило для годовой задачи.
- Дату начала действия правила и возможность задать исключение для конкретного срока.

У клиента выбирается набор шаблонов, ответственный по каждому и период начала обслуживания. Для индивидуальных обязательств, например связанных с конкретным патентом, допускаются собственные даты клиента.

## 5. Автоматическое создание задач

Сроки берутся из правил справочника. Их настраивает руководитель; для демоверсии используем явно помеченные примеры. Планировщик не должен выдавать неподтвержденные демонстрационные даты за проверенный налоговый календарь.

Примеры из ответов заказчика:

| Шаблон | Период | Правило даты |
| --- | --- | --- |
| РСВ | Первый квартал | 25 апреля |
| РСВ | Полугодие | 25 июля |
| РСВ | Девять месяцев | 25 октября |
| РСВ | Год | 25 января следующего года |
| Перс. сведения | Прошлый месяц | 25-е число следующего месяца |

Эти примеры фиксируют желаемую механику и введенные заказчиком даты. Проверка актуальных обязательств и сроков для реальных клиентов выполняется отдельно перед рабочим запуском.

Для платежей поддерживаются ежемесячные, ежеквартальные, ежегодные и индивидуальные графики, включая несколько платежей по одному обязательству. Каждый платеж получает отдельную задачу.

Отчетный период и срок сдачи хранятся раздельно. РСВ за первый квартал попадает в апрель по сроку сдачи, а Перс. сведения за декабрь — в январь следующего года.

Главная таблица по умолчанию показывает месяц или квартал, в котором наступает срок выполнения. В карточке всегда написано, за какой период отчет. Это исключает смешение «за первый квартал» и «сдать в первом квартале».

Задачи создаются при назначении шаблонов и при открытии новых периодов. Повторное открытие страницы или периода не создает дублей. Ключ задачи включает клиента, назначенный шаблон, период и при необходимости номер платежа.

Изменение правила срока применяется к будущим задачам с выбранной даты. История закрытых задач сохраняется. Пересчет уже созданных незакрытых задач должен быть явным действием с предварительным списком изменений.

Переходы через конец года учитываются автоматически. Для дат, которых нет в месяце, справочник должен задавать понятное правило, например последний день месяца. Нельзя молча переносить их в другой месяц.

Переносы из-за выходных и праздников не рассчитываются по одному лишь дню недели. Для первой версии предлагаем ручные исключения по датам; автоматический перенос возможен позднее при подключении и проверке соответствующего календаря.

## 6. Статусы и контроль сроков

Для отчетов предлагаем следующую трактовку:

| Статус | Отображение | Закрывает задачу |
| --- | --- | --- |
| Не сдано | Малиновый/красный акцент с начала месяца срока | Нет |
| Ждем документы | Песочный фон и текст статуса | Нет |
| Отправлено | Синий | Нет, требуется дальнейшее подтверждение |
| Сдано | Зеленый | Да |
| Принято | Зеленый с отдельной отметкой принятия | Да |

«Не сдано» — начальное состояние вместо пустой ячейки статуса. «Принято» дополнительно отличает подтвержденный прием от отметки сотрудника «Сдано». Разделение «Отправлено», «Сдано» и «Принято» — предлагаемая рабочая модель; ее можно уточнить до реализации.

Для платежей используем понятные состояния «Не уплачено», «Ждем документы», «Уплачено», чтобы не называть уплату сдачей отчета. «Уплачено» закрывает платежную задачу.

Правила подсветки:

- Будущие задачи до начала месяца срока отображаются нейтрально.
- С первого дня месяца срока незакрытая задача без промежуточного статуса подсвечивается малиновым. Например, задача на 25 апреля становится активной 1 апреля.
- «Ждем документы» и «Отправлено» получают свой цвет и остаются в счетчике незакрытых.
- Со дня, следующего за сроком, незакрытая задача получает дополнительную заметную метку «Просрочено». Ожидание документов или отправка не должны скрывать просрочку.
- В сам день срока задача еще не считается просроченной; показывается «Срок сегодня».
- Закрытые задачи получают зеленую отметку. Если задача закрыта после срока, дата фактического выполнения сохраняет информацию об опоздании.
- Цвет всегда сопровождается словами, поэтому значение понятно без цветовой легенды.

Предлагаемый критерий просрочки строже первоначального «если статус не поменялся»: просроченной остается любая незакрытая задача после срока. Это защищает от исчезновения просрочки при выборе «Ждем документы».

В карточке задачи: клиент, отчет или платеж, отчетный период, ответственный, срок, статус, дата выполнения и комментарий. В командной версии дополнительно история изменений.

## 7. Главный экран

Верхняя часть:

- Название и фирменная идентификация «Финалогики».
- Переключатель «Месяц / Квартал», год и выбранный период, кнопки перехода назад и вперед.
- Выбор сотрудника или «Все сотрудники».
- Поиск по клиенту.
- Фильтры по статусам, типу обязательства и просрочке.

Ниже — счетчики за выбранный период: всего задач, незакрытых, отправлено, сдано, принято, уплачено, ждем документы, просрочено. Счетчик незакрытых включает промежуточные статусы; просрочка является дополнительным признаком и может пересекаться со статусом. Поэтому все счетчики нельзя складывать как независимые категории.

При выборе конкретного сотрудника счетчики показывают его задачи. В режиме всех сотрудников предлагается компактная сводка по каждому человеку: всего, закрыто, незакрыто и просрочено. Выбор сотрудника в сводке фильтрует таблицу.

Основная таблица:

- Слева закреплено название клиента.
- Следом показан ответственный и его роль. При нескольких ответственных у клиента создаются подстроки, объединенные названием клиента.
- Справа расположены колонки обязательств. В квартальном режиме месяцы сгруппированы, а внутри них показаны соответствующие отчеты и платежи.
- Каждая задача показывает название, отчетный период, дату срока и статус.
- Если за месяц есть несколько задач одного вида, они показываются отдельно внутри ячейки.
- Пустая ячейка обозначает отсутствие назначенной задачи, а не «сдано».
- Заголовки и колонка клиентов остаются видимыми при прокрутке. Для большого набора отчетов используется горизонтальная прокрутка.

Нажатие на задачу открывает боковую карточку для смены статуса и комментария. Сохранение не должно сбрасывать выбранный период и сотрудника.

Логотип не перерисовывается произвольно. Для точного использования нужен пригодный исходник или аккуратное извлечение из предоставленного материала. Временная текстовая идентификация допустима в прототипе.

## 9. Демонстрационные данные и перенос реальных

Первая версия содержит вымышленные данные: 20 сотрудников, примерно 12–15 клиентов, разные наборы отчетов и распределение между главбухами и зарплатниками. Часть клиентов имеет двух ответственных.

Демонстрация включает месячные, квартальные и годовые задачи, платежи, все статусы, просрочки и переход декабрь–январь. Демо помечается явно; загрузка примеров не должна перезаписывать уже введенные пользователем данные.

Таблица реальных клиентов и сотрудников существует, но пока не предоставлена. После ее получения определяется соответствие колонок клиентам, сотрудникам и ролям. Массовый импорт должен иметь предварительный просмотр и проверку повторов. Формат текущей таблицы пока неизвестен.

В локальном прототипе предлагается экспорт и импорт резервной копии JSON с проверкой формата. Это способ переноса копии, а не автоматическая синхронизация команды. Замена данных при импорте должна быть явным действием.

## 10. Границы первой версии

В локальный прототип входят главная таблица, фильтры, счетчики, редактируемые справочники, назначение обязательств и ответственных, автоматические повторяющиеся задачи, статусы, просрочки, комментарии, демонстрационные данные и сохранение после перезагрузки.

На этом этапе не предполагаются отправка отчетности в государственные системы, банковские платежи, хранение отчетных документов, расчет сумм налогов, автоматическая проверка налогового законодательства и внешние уведомления сотрудникам.

Сроки в справочнике — правила, заданные и проверенные компанией. Изменения законодательства сами по себе не обновляют их автоматически.

## 11. Критерии готовности

1. При выборе сотрудника видны только его задачи, при выборе всех — общая картина с исполнителями.
2. У одного клиента разные отчеты могут принадлежать разным сотрудникам.
3. Назначение набора шаблонов создает задачи со сроками из справочника без повторного ручного ввода дат.
4. Месячный и квартальный режимы корректно учитывают переходы между годами и отчетный период отдельно от срока.
5. Повторное открытие периода не создает дубликаты и не сбрасывает статусы.
6. С начала месяца срока незакрытые задачи заметны; после срока появляется метка просрочки.
7. «Ждем документы» не скрывает просрочку, «Сдано» и «Принято» закрывают отчет, «Уплачено» закрывает платеж.
8. Счетчики согласованы с выбранным периодом и сотрудником; пересечения статусов и просрочки понятны.
9. Колонка клиентов закреплена слева, широкая таблица удобна на компьютере.
10. Локальные изменения сохраняются после перезагрузки браузера, резервную копию можно выгрузить и восстановить.
11. В командной версии сохранение руководителем видно сотрудникам на других компьютерах; проверяются права, потеря соединения и одновременное редактирование.

## 12. Что нужно определить перед рабочим запуском

- Согласовать снятие ограничения «только localStorage» для командной версии и выбрать размещение общего хранилища.
- Подтвердить значение промежуточных статусов и правило закрытия задачи.
- Утвердить реальные сроки, годовые правила, платежные графики и исключения.
- Предоставить существующую таблицу клиентов и сотрудников для переноса.
- Уточнить доступ сотрудников к задачам коллег; по умолчанию предлагается доступ только к своим.
- При наличии предоставить исходник логотипа и файлы NT Somic для точного оформления.

Эти пункты не мешают созданию локального демонстрационного прототипа после отдельного поручения на разработку, но необходимы для полноценного командного запуска.
