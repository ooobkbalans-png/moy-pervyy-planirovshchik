# Техническое задание: планировщик отчетности «Финалогика»

Версия: 1.1. Дата редакции: 13 октября 2026 года.

Целевой результат: готовый к показу локальный прототип. ТЗ самодостаточно: разработчику не требуется восстанавливать правила по concept.md. Указанные ниже алгоритмы и проектные настройки не являются утверждениями о законодательных сроках.

## 1. Краткое описание для заказчика

Прототип должен доказать удобство рабочего процесса на 380 клиентах: найти задачи, правильно увидеть сроки, быстро отметить выполнение и обнаружить незавершенную работу. Он также проверяет распределение ответственности и повторяемость задач. Это основа интерфейса и бизнес-логики будущего продукта; производственные серверные механизмы сейчас не нужны.

Три главные функции: план по клиентам с выбором периода и сотрудника; автоматические задачи из справочника сроков; быстрое выполнение со статусами и достоверными показателями. Результат — три файла `index.html`, `styles.css`, `app.js`, локальное сохранение, фирменный дизайн и готовые демоданные. React, backend, настоящий вход, подключение почты, настоящие сообщения MAX и синхронизация между компьютерами не входят в поставку.

Контрольная нагрузка: 20 пользователей, 380 клиентов, 15 экземпляров задач на клиента в квартал, всего 5700 задач. Это тестовый объем, а не запрет добавить шестнадцатую задачу. Разработчик принимает решения о внутренней структуре кода; приемка проверяет поведение продукта.

Ключевые бизнес-правила:

- Сотрудник видит свои задачи; руководитель и менеджер-администратор управляют всеми.
- Отчет «Сдано» больше не является текущей просрочкой сдачи, но остается незакрытым до «Принято». Ожидание приема учитывается отдельно.
- Платеж «Отправлено» закрывает отправку информации клиенту, не подтверждает уплату налога. Срок задачи — законодательный срок уплаты.
- «Ждем документов» — дополнительная отметка, не отменяющая срок.
- Красный акцент с начала месяца сохраняется по требованию заказчика. Просрочка имеет дополнительную рамку, иконку и слова.
- 24 месяца — прямо выбранная заказчиком глубина оперативной истории планировщика, не срок хранения бухгалтерских документов. Автоудаления в прототипе нет.

## 2. Границы локального прототипа

### 2.1. Реализовать

- Демонстрационный вход по почте и переключение между учетными записями.
- Три роли доступа и ограничение действий в интерфейсе и обработчиках операций.
- Главную таблицу клиентов и задач, месячный и квартальный режимы.
- Справочники сотрудников, клиентов, отчетов и платежей.
- Назначение клиенту набора обязательств с отдельным ответственным на каждое.
- Автоматические повторяющиеся задачи и глобальные правила сроков.
- Раздельные статусы отчетов и платежей, отметку ожидания документов, один комментарий.
- Просрочки, старые незакрытые задачи, процент выполнения и нагрузку.
- Передачу ответственности по выбранным клиентам.
- Статус клиента «Снят», архивирование и сохранение истории.
- Импорт CSV из выгрузки Google Sheets с сопоставлением колонок.
- Настоящую выгрузку XLSX и резервную копию JSON.
- Раздел напоминаний за два дня до срока; предпросмотр MAX — Should.
- Восстановление после перезагрузки и проверку ошибок хранения; предупреждение о второй вкладке — Should.

### 2.2. Не включать в приемку прототипа

Реальные входящие письма и проверку владения почтой; пароли; синхронизацию между компьютерами; защищенное серверное разграничение доступа; отправку в MAX; фоновую доставку уведомлений при закрытом браузере; прямое подключение к Google Sheets; отправку отчетов в государственные системы; банковские платежи; суммы налогов; вложения; переписку; произвольные поручения; массовую смену статусов; индивидуальные сроки клиентов; автоматическую проверку законодательства.

На экране входа и в разделе «О прототипе» показывать: «Локальный прототип. Данные хранятся в этом браузере. Вход и права демонстрационные; между компьютерами данные не передаются». Не представлять фильтрацию интерфейса как защиту файлов от владельца компьютера.

## 3. Роли и должности

Роль определяет права, должность — характер работы. Это разные поля.

Роли: `owner` — Руководитель; `admin` — Администратор; `employee` — Сотрудник.

Должности: Главный бухгалтер, Зарплатник, Администратор, МатСтол. Один человек может иметь несколько должностей. Должность «Администратор» автоматически не дает роль `admin`: роль назначается отдельно.

### 3.1. Матрица прав

| Действие | Руководитель | Администратор | Сотрудник |
| --- | --- | --- | --- |
| Просмотр всех активных клиентов и задач | Да | Да | Нет |
| Фильтр «Все сотрудники» и выбор любого сотрудника | Да | Да | Нет |
| Просмотр своих клиентов и своих задач | Да | Да | Да |
| Изменение статуса, ожидания документов и комментария своей задачи | Да | Да | Да |
| Те же действия с чужой задачей | Да | Да | Нет |
| Изменение сроков непосредственно в задаче | Нет | Нет | Нет |
| Управление клиентами, назначениями и справочником сроков | Да | Да | Нет |
| Передача задач по выбранным клиентам | Да | Да | Нет |
| Добавление, редактирование и архивирование сотрудников | Да | Да, кроме руководителя | Нет |
| Назначение роли сотрудника или администратора | Да | Да, кроме своей роли | Нет |
| Передача роли руководителя через UI | Да | Нет | Нет |
| Импорт CSV, резервное восстановление и очистка демо | Да | Да | Нет |
| Экспорт XLSX | Все доступные данные | Все доступные данные | Только свои задачи |
| Экспорт полной резервной копии JSON | Да | Да | Нет |
| Архив и история всех клиентов | Да | Да | Только история собственных задач |
| Общая нагрузка по сотрудникам | Да | Да | Только личная сводка |

Руководитель один. Он может выполнить «Передать роль руководителя»: выбрать другого активного пользователя, увидеть предварительный просмотр, ввести слово «ПЕРЕДАТЬ» и подтвердить. Новый пользователь получает owner, прежний — admin; операция атомарна, записывается в историю, права текущей сессии немедленно обновляются. Править JSON не нужно. Нельзя архивировать текущего руководителя или последнего действующего администратора. Администратор не может повысить себя до руководителя, менять запись руководителя или архивировать свою текущую учетную запись. Руководитель может назначить другого администратора и затем архивировать прежнего.

Запрет сотруднику «править» означает запрет управлять справочниками, назначениями и сроками. Изменение статуса, дополнительной отметки и одного комментария своей задачи разрешено, включая возврат статуса назад.

## 4. Демонстрационный вход и сотрудники

### 4.1. Вход

Форма: поле «Рабочая почта», кнопка «Войти в прототип» и список демонстрационных аккаунтов для быстрого заполнения. Письма и пароли не используются. Только активная запись с совпавшей почтой допускает вход. Иначе показать «Активный сотрудник с такой почтой не найден» без создания аккаунта.

Почта сравнивается после удаления пробелов по краям и приведения к нижнему регистру. Текущую демонстрационную сессию хранить в sessionStorage; основные данные — в localStorage. После перезагрузки вкладки сессия сохраняется, после выхода очищается. При входе заново проверять активность записи и роль.

В шапке показать имя, роль и кнопку «Выйти». Сотрудник видит там собственное имя, но не список коллег. У руководителя и администратора отдельно находится фильтр исполнителя, который не меняет вошедшую учетную запись.

### 4.2. Карточка сотрудника

Поля: ФИО/отображаемое имя, рабочая почта, роль, одна или несколько должностей, статус «Активен / В архиве». Поле идентификатора MAX отсутствует в прототипе.

Имя обязательно, 2–120 символов. Почта обязательна, до 254 символов, валидируется как email, уникальна среди всех записей, включая архив. Пробелы по краям удаляются. Должность обязательна хотя бы одна.

При архивировании сотрудника с активными назначениями сначала потребовать передать их или завершить обслуживание соответствующих клиентов. Нельзя создавать бесхозные задачи. История архивного сотрудника сохраняется; его нет в списке выбора новых ответственных. Восстановление сохраняет его идентификатор и историю, но не возвращает переданные назначения автоматически.

## 5. Клиенты и назначения

### 5.1. Карточка клиента

Обязательное пользовательское поле — наименование (2–200 символов). Дополнительное необязательное поле — СНО, поскольку оно есть в исходной таблице. СНО — текстовая справочная метка до 120 символов; она не назначает обязательства автоматически.

Статус клиента: `active` — «Активен»; `removed` — «Снят». Отдельных дат начала и окончания обслуживания в форме нет. Системные даты создания и снятия сохраняются для истории, но не вводятся пользователем.

Одинаковые нормализованные названия запрещены: сравнение без регистра, повторяющихся пробелов и пробелов по краям. ИНН не используется. При необходимости различать одноименных клиентов пользователь уточняет название.

### 5.2. Набор обязательств

При создании или редактировании клиента администратор/руководитель выбирает шаблоны. Для каждого выбранного шаблона указывает одного активного ответственного и должность назначения. Один человек может вести несколько видов обязательств одного клиента. Разные виды могут принадлежать разным людям.

Отчет и платеж выбираются отдельно. Для одного клиента один шаблон может иметь только одно активное назначение. Отсутствие ответственного блокирует сохранение. Должность назначения должна входить в должности выбранного сотрудника.

Не показывать сотруднику чужие обязательства даже по общему клиенту. Например, главбух видит НДС по клиенту, но не РСВ зарплатника.

При добавлении клиента и новых обязательств задачи появляются начиная с первого числа текущего месяца по сроку выполнения. Если сегодня 20 октября, задача со сроком 10 октября создается и сразу считается просроченной; задачи со сроком в сентябре не создаются. Правило относится к месяцу срока, а не к отчетному периоду.

Системный `generationStartMonth` фиксируется при назначении и не сдвигается при повторном открытии приложения.

### 5.3. Снятие клиента

Действие доступно только руководителю/администратору, требует подтверждения с количеством затрагиваемых незакрытых задач.

После подтверждения:

- Клиент получает статус «Снят».
- Его незакрытые задачи получают техническую отмену с причиной «Клиент снят с обслуживания».
- Новые задачи не создаются.
- Все его задачи исключаются из рабочего плана, напоминаний, счетчиков и нагрузки.
- Закрытая история сохраняется в разделе «История и архив»; отмененные записи также доступны там с причиной.

Восстановление клиента возможно в карточке архива. Администратор подтверждает набор обязательств и актуальных сотрудников. Генерация возобновляется с текущего месяца. Ранее отмененные задачи не оживают автоматически. Для нового назначения создается новый идентификатор, поэтому исторические задачи не смешиваются с новым циклом обслуживания.

### 5.4. Снятие отдельного обязательства

В карточке активного клиента руководитель/администратор может архивировать выбранное назначение. После подтверждения оно больше не создает задачи, незакрытые задачи отменяются с причиной «Обязательство снято», закрытая история сохраняется. Это управление справочником клиента, а не массовое действие из главной таблицы.

## 6. Справочник отчетов и платежей

Начальные наименования семейств: НДС, Налог на прибыль, Налог на имущество, Транспортный налог, РСВ, 6-НДФЛ, ЕФС-1, Перс. сведения, УСН, Патент. Семейство не означает, что обязательно существуют оба типа задач или что все они нужны каждому клиенту.

Шаблон содержит:

| Поле | Правило |
| --- | --- |
| Название | Обязательно, 2–120 символов |
| Тип | `report` — отчет; `payment` — налог/платеж |
| Семейство | Одно из начальных или новое название |
| Рекомендуемая должность | Одна из четырех; подсказка, не автоматическое назначение |
| Периодичность | Месяц, квартал, год, явный календарный график |
| Правила сроков | По разделу 7 |
| Статус | Активен / Архив |
| Пометка дат | Демонстрационные / Проверены компанией |

Название и тип в совокупности уникальны без учета регистра и лишних пробелов. Редактирование наименования не меняет идентификатор. Тип, периодичность и идентификаторы повторов после появления назначений нельзя менять; для другой структуры создается новый шаблон. Можно изменять даты, подписи и должность по умолчанию.

Архивирование шаблона требует предварительного списка активных назначений и подтверждения. Эти назначения архивируются, незакрытые задачи отменяются с причиной «Шаблон архивирован», закрытая история сохраняется. Если пользователь не подтвердил, никаких изменений нет.

В справочнике и демо показывать: «Даты задаются компанией. Демонстрационные сроки не являются проверенным налоговым календарем». Не заполнять неизвестные реальные сроки как будто они проверены.

## 7. Сроки, рабочий календарь и тестовая дата

### 7.1. Единая текущая дата

Часовой пояс — Asia/Yekaterinburg. Даты сроков и фактических действий — YYYY-MM-DD, время аудита — настоящее UTC ISO 8601.

В «О прототипе → Тестирование» руководитель/администратор может установить «Текущую дату для теста» либо вернуть настоящую дату. Настройка сохраняется для локального набора. Во всех разделах при подмене видна плашка «ТЕСТОВАЯ ДАТА: ДД.ММ.ГГГГ», в экспортах — пометка. Сотрудник видит плашку, но не меняет дату.

Все календарные вычисления используют effectiveToday: текущий месяц, генерация, просрочки, напоминания, фактические даты по умолчанию. Настоящее время аудита не подменяется. Перевод даты не изменяет сохраненные фактические даты и начало назначений. Запрет будущей даты проверяется при ее вводе; при переводе тестовых часов назад уже записанные даты не удаляются.

### 7.2. Форматы правил

1. Месяц: отчетный месяц, смещение месяца срока 0–12, число 1–31.
2. Квартал: четыре периода, постоянные slotId, смещение месяца от конца квартала 0–12, число. Возможны несколько повторов платежа. У РСВ четвертый период имеет подпись «Год», технический ключ Q4.
3. Год: отчетный год, месяц, смещение года 0–1, число.
4. Явный график: постоянный slotId, период и абсолютная дата. Общий для клиентов шаблона; недостающие будущие даты не придумываются.

Для несуществующего числа выбрать «Последний день месяца» либо «Ошибка правила» (по умолчанию ошибка). Опция шаблона «Переносить на следующий рабочий день» включается после проверки ее применимости компанией; не считать налоговое правило универсальным для любых отчетов.

### 7.3. Рабочий календарь

В «Отчеты и платежи → Рабочий календарь» руководитель/администратор задает год, область применения, источник, проверяющего, дату проверки, статус «Демонстрационный / Проверен компанией». Даты-исключения включают нерабочие будни и рабочие субботы/воскресенья. Форма даты: «Рабочий / Нерабочий / По умолчанию». Календарь привязывается к шаблону; при разных областях применения допускается несколько календарей, но не персональные сроки клиента.

Демо-календарь — пятидневка с явно тестовыми исключениями, не официальный производственный календарь. Менеджер заполняет, главный бухгалтер проверяет календарь до реального планирования соответствующего года. Автоматического скачивания нет. При отсутствии нужного года показать ошибку «Не заполнен календарь YYYY», счетчик ошибок настройки и не выдавать непроверенный расчет за точную дату. Реальная конфигурация с такими ошибками не считается готовой; для демонстрационной навигации разрешен помеченный тестовый календарь нужного года.

### 7.4. Алгоритм расчета

1. Определить назначение, отчетный период, slotId и taskKey = assignmentId:periodKey:slotId.
2. Для закрытой/отмененной задачи использовать сохраненный снимок срока.
3. Для остальных вычислить номинальную дату из правила, обработать несуществующее число выбранной политикой.
4. При наличии общего исключения для шаблона/периода/slotId использовать его как окончательную дату, без повторного переноса. В форме подписать «Окончательная дата, включая переносы».
5. Иначе при включенном переносе: явная рабочая дата календаря приоритетнее дня недели; затем учитывать явную нерабочую, затем пятидневку. Пока дата нерабочая, прибавлять один календарный день.
6. При переходе года использовать календарь нового года; если его нет, остановиться с ошибкой, не угадывать дату и не продолжать бесконечный цикл.
7. Применить фиксированную границу начала назначения. Если правка переносит уже существующую задачу раньше границы, показать конфликт в предварительном просмотре и не скрывать задачу молча.
8. Месяц/квартал отображения определить по окончательной дате срока; отчетный период не менять.
9. При изменении правила, календаря или исключения показать старые/новые даты и затронутые незакрытые задачи всех клиентов. По подтверждению пересчитать их, сохранив статусы, исполнителей, комментарии и фактические даты. Закрытые/отмененные снимки не менять.
10. Перенос даты не меняет taskKey и не создает дубль. При возврате закрытой задачи в работу использовать актуальное правило с предупреждением об изменении срока.

Срок нельзя менять в карточке клиента или задачи. Индивидуальных клиентских исключений нет.

### 7.5. Проверка реальных правил

Менеджер заполняет, назначенный руководителем главный бухгалтер проверяет применимость/периодичность/даты, руководитель разрешает работу с реальными планами. Для проверенной записи обязательны проверяющий, дата и источник. Стартовый набор приведен в приложении Б.

Контрольная точка проверки — до первого импорта реальных клиентов и до начала очередного года. Конкретную дату проверки согласуют руководитель и менеджер, разработчик ее не выдумывает. Для написания и демонстрации используются помеченные тестовые сроки.

## 8. Генерация и история

Задача однозначно определяется назначением, периодом и slotId. Повторные открытия месяца и перезагрузка не создают дублей и не сбрасывают состояние. Хранение вычисляемых либо материализованных задач — выбор разработчика, если соблюдены поведение и производительность.

Новые назначения генерируют задачи со сроком начиная с первого числа текущего месяца effectiveToday. Начальный месяц фиксируется один раз. При пропуске месяцев положенные незакрытые задачи не теряются, даже если приложение тогда не открывали. Будущие повторения не создавать бесконечным массивом.

Закрытая история хранит снимки названия клиента/шаблона, исполнителя, срока, фактических дат. Передача назначения не переписывает закрытую историю. При снятии отменяются измененные открытые задачи и неизмененные повторения до конца текущего месяца; неизмененные будущие повторения просто перестают генерироваться. Ранее измененная будущая задача также сохраняется отмененной.

24 месяца — глубина оперативной истории, прямо указанная заказчиком; она не задает сроки хранения бухгалтерских документов. В прототипе по умолчанию отображать последние 24 месяца с фильтром «Все сохраненные данные», но ничего автоматически не удалять. Старые незакрытые долги показывать независимо от возраста. terminalKeys, ежедневная очистка и автоматические миграции схем сейчас не нужны. Политика удаления и возможное увеличение срока — предмет будущего этапа, не замена ответа заказчика на 4–5 лет.

## 9. Статусы, завершение и комментарии

### 9.1. Отчеты

| Код | Надпись | Значение | Закрыт |
| --- | --- | --- | --- |
| `pending` | Не сдано | Начальный статус | Нет |
| `submitted` | Сдано | Отчет отправлен, прием еще не подтвержден | Нет |
| `accepted` | Принято | Прием подтвержден сотрудником | Да |

Для отчетов статус «Отправлено» отсутствует. Статус «Отклонено» отсутствует.

### 9.2. Платежи

| Код | Надпись | Значение | Закрыт |
| --- | --- | --- | --- |
| `pending` | Не отправлено | Информация/напоминание по уплате еще не отправлены | Нет |
| `sent` | Отправлено | Сотрудник выполнил действие по налогу | Да |

Статус «Отправлено» не утверждает, что клиент фактически уплатил налог. Суммы, подтверждение банка и статусы «Уплачено» не предусмотрены. Срок в такой задаче — срок уплаты из справочника; в интерфейсе подписать «Уплата до …».

### 9.3. Переходы

Сотрудник может менять свою задачу между любыми допустимыми статусами ее типа; сразу отметить отчет принятым можно с указанием фактических дат сдачи и принятия. Руководитель/администратор делают это для любой активной задачи. Возврат закрытого статуса требует подтверждения, удаляет текущий `closedAt`, восстанавливает незакрытость и пересчитывает просрочку. Предыдущие события остаются в истории.

При завершении closedAt фиксирует настоящее время записи, а не фактическую дату действия. Снять waitingDocuments, сохранить снимок срока и исполнителя. При «Сдано» обязательна фактическая дата сдачи; при «Принято» — даты сдачи и принятия; при платеже «Отправлено» — дата отправки информации. Значение по умолчанию effectiveToday, пользователь своей задачи может исправить его. Будущая дата запрещена, принятие не раньше сдачи. Возврат в «Не сдано» снимает обе даты, из «Принято» в «Сдано» — только принятие; возврат платежа снимает отправку. Аудит прежних значений сохраняется. Фактические даты может уточнять ответственный или руководитель/администратор; законодательный срок не редактируется.

С датой сдачи/отправки фиксировать `actionDueDate` — действовавший срок действия. Историческая своевременность сравнивается с ним, а не со временем клика или изменившимся позднее правилом. При прямом принятии отчета также сохранить actionDueDate. Изменение фактической даты сохраняет этот снимок; возврат в начальный статус снимает его вместе с фактическими датами. Снимок срока закрытия для отображения истории хранится отдельно. Журнал позволяет увидеть, по какому сроку оценивалась сдача.

### 9.4. Ожидание документов

`waitingDocuments` — независимый boolean, а не основной статус. Может сочетаться с «Не сдано», «Сдано» и «Не отправлено». У закрытой/отмененной задачи нельзя включить ожидание документов; при завершении флаг автоматически снимается. Возврат задачи назад не восстанавливает флаг автоматически.

Ожидание не меняет срок, не исключает задачу из просрочек и не закрывает ее.

### 9.5. Комментарий

Один редактируемый текст, до 2000 символов, без форматирования и вложений. Пустой допустим. Пробелы по краям удаляются. Показывать автора и время последнего изменения. Изменения комментария фиксировать в аудите в пределах срока хранения. Сотрудник может менять единое примечание своей доступной задачи независимо от автора последней редакции, в том числе после правки администратора; это не личное сообщение автора. Руководитель/администратор могут менять примечание любой доступной задачи. В закрытой задаче комментарий можно уточнять, статус при этом не меняется. Отмененные/архивные задачи доступны только для чтения.

## 10. Просрочки и визуальные признаки

### Отчет

- Закрыт только в статусе «Принято».
- Текущая просрочка сдачи: активный отчет «Не сдано», dueDate < effectiveToday.
- «Сдано с опозданием»: фактическая дата сдачи позже снимка срока; исторический признак, не текущая просрочка.
- «Сдано» не является текущей просрочкой сдачи, но ожидает принятия и остается незакрытым.
- Отдельная метка «Долго ожидает принятия»: статус Сдано, календарных дней после фактической сдачи больше 3. Порог 3 — внутренняя проектная настройка прототипа, не законодательный срок; руководитель/администратор могут задать 1–30. Ожидание приема не суммировать с просрочкой сдачи.

### Платеж

Задача контролирует отправку информации, а ее общий срок — законодательная дата уплаты. «Не отправлено» после этой даты обозначается «Информация не отправлена к сроку уплаты». «Отправлено» закрывает задачу; отправка после срока определяется фактической датой. Это не подтверждение оплаты, статус «Налог не уплачен» не выводить.

Новый обязательный срок «сообщить клиенту до» без согласования не вводить: заказчик запретил особые сроки. За два дня до уплаты показывать напоминание об информации. В справке объяснить, что отметка отправки в последний день не гарантирует клиенту времени для оплаты.

### Цвета

До начала месяца срока начальные задачи нейтральные; с начала месяца — малиновая точка/полоса на светлом фоне по требованию заказчика. Просрочка дополнительно имеет контрастную рамку, иконку и точную подпись. Не использовать одинаковое оформление для всего месяца и просрочки.

Сдано — зеленая метка «Ожидает принятия», Принято — зеленая с завершением, платеж Отправлено — синий. Ждем документов — дополнительная песочная метка. «Осталось 2 дня», «Остался 1 день», «Срок сегодня» считаются календарно. В день срока просрочки нет. Долгое ожидание принятия — отдельная песочная метка. Пересчет при открытии, возврате в фокус и смене дня. Все цвета сопровождаются текстом, целую строку клиента ярким фоном не заливать.

## 11. Экраны и навигация

Меню: «План», «Мои клиенты», «Напоминания», «История». Руководителю/администратору дополнительно: «Клиенты», «Сотрудники», «Отчеты и платежи», «Нагрузка», «Импорт и резервные копии». Кнопка «О прототипе» доступна всем.

Разделы переключаются без перезагрузки страницы. Нельзя обойти права прямой ссылкой на раздел или ручным вызовом штатного обработчика: каждый метод изменения повторно проверяет роль и доступ к задаче. Это логическая проверка, не серверная безопасность.

### 11.1. Главная таблица

Верхняя панель:

- Месяц/Квартал, год, выбранный месяц или квартал.
- Назад, вперед, «Текущий период».
- Фильтр сотрудника только для руководителя/администратора; значение по умолчанию «Все сотрудники».
- Поиск клиента.
- Фильтры типа, основного статуса, «Ждем документов», «Просрочено».
- Кнопка Excel.

Сотрудник не выбирает коллег или «Все сотрудники». Его имя показывается в той же верхней строке как фиксированный элемент.

Одна строка соответствует одному клиенту. Ответственных под названием клиента не выводить. В месячном режиме справа колонки обязательств, в квартальном — группы трех месяцев, внутри колонки обязательств. Включать только шаблоны, для которых есть задачи в доступном пользователю наборе; сортировать по типу (отчеты, затем платежи) и названию, месяцы — по календарю.

В ячейке карточки задач со сроком, подписью периода и статусом. Несколько повторов одного платежа показываются отдельно по возрастанию срока. Отсутствие задачи — прочерк, не зеленая отметка.

В режиме всех сотрудников в карточке задачи показывать короткое имя исполнителя; при выбранном сотруднике имя в ячейке не повторять. Полное имя всегда есть в боковой карточке. Это обеспечивает обзор без дополнительных строк под клиентом.

Колонка клиентов и заголовки закреплены при прокрутке. Широкая таблица прокручивается горизонтально внутри своего контейнера. Не сжимать текст до нечитаемого размера. Клиенты сортируются по русскому алфавиту. Дополнительная сортировка «Сначала просроченные» (Should) поднимает клиентов с просрочкой, внутри группы сохраняет алфавит.

### 11.2. Старые незакрытые задачи

Над таблицей постоянный блок «Не закрыто из предыдущих периодов»: задачи со сроком раньше начала выбранного периода, доступные текущему пользователю. Он раскрыт по умолчанию при наличии записей. Показывать клиента, обязательство, период, ответственного в общем режиме, срок, основной статус и дни просрочки.

Задачи из этого блока не дублируются в основной таблице. Если выбран будущий период, сюда могут попасть незакрытые задачи с еще не наступившим сроком; не помечать их просроченными до наступления даты. Название блока относится к выбранному периоду, а просрочка — к сегодняшнему дню.

### 11.3. Боковая карточка задачи

Поля только для чтения: клиент, название, тип, отчетный период, ответственный, должность, срок, текущая просрочка, дата закрытия. Редактируемые: допустимый статус, фактические даты, ожидание документов, комментарий. Срок и назначенный сотрудник только для чтения. Кнопки «Сохранить», «Отмена». Если изменений нет, «Сохранить» неактивна.

При закрытии карточки с несохраненными изменениями спросить «Сохранить / Не сохранять / Продолжить редактирование». После сохранения не сбрасывать фильтры и прокрутку. Если задача исчезла из текущего фильтра, объяснить это сообщением.

### 11.4. Быстрая смена статуса

Кнопка статуса в ячейке открывает компактное меню без боковой карточки. Выбор показывает необходимые фактические даты, по умолчанию сегодня; Enter/подтверждение сохраняют, Escape отменяет. Возврат назад требует подтверждения. Ожидание документов можно переключать отдельной кнопкой. После успеха обновить метку/счетчики без сброса периода, фильтров и прокрутки. При ошибке вернуть прежний статус и сохранить введенное в форме. Массовой смены нет. Карточка остается для примечания и подробностей.

### 11.5. Мои клиенты

Список своих активных клиентов независимо от выбранного периода: название, СНО, собственные назначенные обязательства, число открытых и просроченных задач. Поиск по названию, переход к задачам клиента в плане. Чужие назначения не показывать. Для руководителя/администратора это представление выбранного сотрудника; общий редактируемый каталог — в «Клиенты». Подстрок ответственных в главной таблице нет.

## 12. Счетчики, процент выполнения и нагрузка

Фильтр сотрудника и выбранный период определяют базовый набор P: все активные задачи со сроком в периоде. Снятые клиенты и отмененные задачи исключаются. Текстовый поиск, фильтры статусов и просрочки меняют таблицу, но не знаменатель основных счетчиков; рядом написать «Сводка за период» и отдельно «В таблице найдено N задач».

Основная сводка:

- Всего = |P|.
- Завершено = количество закрытых в P.
- Осталось = всего минус завершено.
- Выполнение = завершено / всего × 100%, округление до одного десятичного знака. При нуле задач показать «Нет задач», не 100%.
- Просрочено в периоде = текущие просрочки по разделу 10; Сдано и ожидание принятия не входят. Отдельно показать просрочку сдачи и неотправленную информацию по платежам, сумму назвать «Текущие просрочки действий».
- Ждем документов = незакрытые P с соответствующей отметкой.
- Сдано / Принято / Отправлено = счетчики соответствующих статусов P.
- Сдано/отправлено с опозданием = фактическая дата сдачи или отправки информации позже снимка срока. Дата принятия и время клика не влияют на метрику. Отдельные счетчики «Ожидают принятия» и «Долго ожидают» не суммировать с просрочкой сдачи.

Старые незакрытые задачи считать отдельно: «Не закрыто из предыдущих периодов: N», «Из них просрочено: M». Не добавлять их в процент выполнения выбранного периода. Общий открытый объем работы = осталось в периоде + не закрыто из предыдущих периодов.

Раздел «Нагрузка» доступен руководителю/администратору: строка на сотрудника, число различных активных клиентов с назначениями, задач в периоде, завершенных, оставшихся, ранее незакрытых, просроченных среди этих двух наборов, ожидающих документы и процент выполнения P сотрудника. Нагрузка измеряется количеством задач, не часами и не денежной стоимостью. Один клиент у разных исполнителей учитывается у каждого; общий итог клиентов рассчитывается по уникальным клиентам, а не суммой строк.

## 13. Передача по выбранным клиентам

Отдельный мастер в разделе «Сотрудники» или «Клиенты»: исходный сотрудник, один новый сотрудник, список выбранных активных клиентов. Список ограничен клиентами, у которых есть активные назначения исходного сотрудника.

Для выбранных клиентов передаются все активные назначения исходного сотрудника и все его незакрытые задачи по этим назначениям, включая старые. Назначения других сотрудников не меняются. Новый сотрудник должен иметь требуемые должности; при несовпадении блокировать передачу с указанием клиентов/шаблонов. Статусы, сроки, комментарии и флаги сохраняются. Будущие задачи получают нового ответственного. Закрытые задачи сохраняют исторического исполнителя.

До применения показать список клиентов, назначений и число незакрытых задач. Операция атомарная: все или ничего. Записать аудит. Это постоянная передача; автоматический возврат после отпуска в прототип не входит. Вернуть обязанности можно тем же мастером.

## 14. История и архив

Фильтры: клиент, сотрудник (кроме обычного сотрудника), тип, период по сроку, закрыто/отменено, включение снятых клиентов. История — плоский список задач, не рабочая матрица. У сотрудника доступ только к задачам, где историческим исполнителем был он; чужие задачи того же клиента не показывать.

В карточке истории — снимок данных и журнал событий. История закрытых задач активного клиента допускает возврат в работу при наличии текущих прав и активного назначения; если задача после передачи принадлежит другому исполнителю, прежний сотрудник ее не меняет. Возврат выполняет текущий ответственный или администратор/руководитель. История отмененных задач и снятых клиентов только для чтения.

При передаче назначения закрытая задача прежнего исполнителя не показывается новому сотруднику как его личная история. Вернуть такую задачу в работу может руководитель/администратор; после возврата она появится у нового ответственного. Прежний сотрудник сможет видеть историческое событие своего закрытия, но не изменять актуальную чужую задачу.

Аудит фиксирует создание/изменение справочников, назначение, смену статуса, ожидания и комментария, пересчет сроков, передачу, снятие и восстановление клиента, архивирование, импорт и восстановление копии. Не хранить токены и пароли.

## 15. Напоминания и MAX в прототипе

### 15.1. Работающий локальный раздел

В разделе «Напоминания» показать доступные пользователю отчеты «Не сдано» и платежи «Не отправлено» с `dueDate = effectiveToday + 2 календарных дня`, независимо от выходных. Дополнительно вкладки «Срок сегодня», «Просрочено» по правилам раздела 10 и «Ожидают принятия». У руководителя/администратора есть фильтр сотрудника.

Пересчет при открытии и смене календарного дня. Предпросмотр сообщения — Should. Если реализован, для каждого исполнителя можно открыть текст:

«Финалогика. Напоминание: через 2 дня, ДД.ММ.ГГГГ, наступает срок. Клиент — обязательство — отчетный период — текущий статус». Отметка ожидания документов выводится в тексте. Для платежа писать «Срок уплаты; проверьте отправку информации клиенту». В двухдневные напоминания включать только отчеты Не сдано и платежи Не отправлено. Для Сдано — отдельная вкладка «Ожидают принятия», без напоминания о сдаче.

Кнопка «Скопировать текст» копирует предпросмотр, при недоступном Clipboard API открывает выделяемое поле для ручного копирования. Не ставить отметку «Доставлено в MAX». Показывать подпись «Предпросмотр. Отправка в MAX появится в командной версии».

Не хранить токен бота в localStorage, исходниках или форме. Не выполнять реальные запросы к MAX из прототипа.

### 15.2. Граница прототипа

Потребность реальной доставки MAX сохранена только в перечне будущих работ раздела 21. Не создавать серверный планировщик, API, бота или токен в прототипе.

## 16. Импорт из Google Sheets

Прямую ссылку и доступ к исходной таблице заказчик пока не предоставил. Прототип работает с локальным CSV, выгруженным из Google Sheets. Показать инструкцию: «В Google Sheets скачайте нужный лист как CSV и выберите файл здесь». Таблица не запрашивается из аккаунта автоматически.

### 16.1. Входной формат

Поддержать UTF-8 с BOM и без, разделители запятая, точка с запятой и табуляция, кавычки и переносы строк в кавычках. Предложить автоматически определенный разделитель и возможность выбрать другой. Размер до 5 МБ, максимум 10 000 непустых строк. Исходный файл и весь его текст постоянно в localStorage не сохранять.

Поля сопоставления:

- Наименование клиента — обязательно.
- СНО — необязательно.
- Вид обязательства/название шаблона — обязательно для назначения.
- Тип (отчет/платеж) — если название неоднозначно.
- Ответственный: рабочая почта предпочтительна; имя разрешается только при единственном совпадении.
- Должность — при необходимости выбора среди нескольких должностей сотрудника.
- Срок — необязательное поле только для сверки с общим справочником.

Сопоставление широкой таблицы — Should: ручное добавление нескольких групп «колонка отчета + колонка сотрудника + необязательная колонка срока». Одна строка клиента разворачивается в несколько назначений. Не угадывать значение произвольной колонки. Если виды отчетов разнесены по колонкам с отметками, группа задает фиксированный шаблон и значение наличия: непустое / «Да» / «1». Для обязательного простого импорта одна строка содержит одного клиента, один шаблон и одного ответственного; несколько строк одного клиента объединяются по его нормализованному имени.

Если исходная строка содержит срок, для сверки обязательны отдельные поля отчетного периода (`YYYY-MM`, `YYYY-QN`, `YYYY`) и slotId, если повторов несколько. Формат даты при сопоставлении выбирается явно: YYYY-MM-DD или ДД.ММ.ГГГГ. Строка без однозначного периода/повтора имеет ошибку сверки, а не сравнивается с произвольной ближайшей задачей. При отсутствии колонки срока эти поля не нужны: назначение берет весь график из справочника.

### 16.2. Правила обработки

1. Прочитать файл, показать первые 20 строк и формы сопоставления.
2. Найти клиентов по нормализованному названию, сотрудников по почте либо однозначному имени, шаблоны по названию и типу.
3. Не создавать сотрудников без рабочей почты и не создавать шаблоны с непроверенными сроками автоматически. Неизвестные записи показать как ошибки с предложением сначала заполнить справочники.
4. Названия клиентов без совпадений создаются при подтверждении. Для существующего клиента импорт может заполнить пустое СНО; замену непустого СНО показать в предварительном просмотре.
5. Новые назначения создаются с текущего месяца. Совпадающие активные назначения пропускаются. Если ответственный отличается, вывести конфликт и потребовать отдельную передачу, не менять его молча.
6. Сроки из строк не записываются как клиентские. При расхождении со справочником показать ошибку сверки. Для разных сроков одного шаблона в одном периоде не выбирать произвольный.
7. Показать сводку: новые клиенты, назначения, пропуски и ошибки. По умолчанию «Только без ошибок». Явная опция «Пропустить строки с ошибками» разрешает импорт валидных строк; показать число пропущенных и скачать CSV ошибок (строка, клиент, поле, значение, причина). Для широкой таблицы ошибка любой группы пропускает всю исходную строку клиента. Валидный пакет сохраняется атомарно; частичная загрузка не означает запись по одной строке.
8. Применить атомарно; при ошибке сохранения ничего не менять. Повторный импорт того же файла не создает дублей и не сбрасывает статусы.

Импорт не удаляет записи, отсутствующие в файле, и не возвращает автоматически снятого клиента. Такие совпадения требуют ручного восстановления вне импорта.

## 17. Excel и резервные копии

### 17.1. XLSX

Кнопка Excel формирует настоящий `.xlsx`, а не HTML/CSV с переименованным расширением. Листы: «Задачи», «Сводка», «Параметры». В разделе истории экспортировать текущий исторический набор вместо рабочего, с указанием режима в параметрах.

Рабочий экспорт содержит задачи основной таблицы и блока старых, соответствующие текущим поиску и фильтрам. Выгружаются все найденные строки, не только визуально отрисованные. Сотрудник никогда не получает чужие данные. Сводка формируется по экспортируемому набору и подписывается «По выгруженным задачам», чтобы не смешивать ее с базовой сводкой за период.

Колонки задач: клиент, СНО, сотрудник, почта сотрудника, должность назначения, тип, обязательство, отчетный период, срок, статус, ждем документов, просрочено, дней просрочки, сдано/отправлено с опозданием, фактическая дата сдачи, фактическая дата принятия, фактическая дата отправки информации, время записи завершения, комментарий, состояние клиента, причина отмены (для истории), признак «Не закрыто из предыдущих периодов».

Даты Excel должны быть датами с форматом `dd.mm.yyyy`, числовые показатели — числами, остальные значения — строками. Включить автофильтр и разумную ширину колонок. Закрепление строки заголовков — Should при поддержке библиотекой; отдельный редактор OOXML ради него не нужен. Пользовательские строки, начинающиеся с `=`, `+`, `-`, `@`, записывать строковым типом, никогда как формулы. Имя файла: `finalogika_tasks_YYYY-MM-DD.xlsx`.

Использовать готовую библиотеку, например SheetJS Community Edition под Apache 2.0, встроенную в app.js. Зафиксировать ее фактическую версию, сохранить требуемые полные LICENSE/NOTICE и авторские уведомления внутри app.js; в справке показать атрибуцию. CDN во время работы нет, данные наружу не передаются. Самописный ZIP/XLSX-генератор не требуется.

### 17.2. JSON

Полная копия содержит версию схемы, время экспорта, правила, календари, справочники, назначения, состояния задач и историю. Сессию не включать. Формат — UTF-8 JSON. Имя: `finalogika_backup_YYYY-MM-DD_HH-mm.json`.

Восстановление заменяет весь набор, а не объединяет его. Проверить схему, типы, ссылки, допустимые статусы, уникальность ID/почт, наличие одного руководителя и хотя бы одного активного администратора. Файл неизвестной будущей версии отклонить. При ошибке показать понятное описание, данные не менять.

До замены показать сводку и предложить скачать текущую копию; требуется явное подтверждение. После успешного восстановления завершить текущую сессию и открыть экран входа. Восстановление должно быть атомарным.

## 19. Нефункциональные требования

Три файла HTML, CSS, JS; без React, сборщика и обязательной установки зависимостей. Библиотечный код Excel включается в app.js. Основной запуск — двойным щелчком в Chrome на Windows, минимум Chrome 120. При приемке записать полную фактическую версию и проверить актуальный стабильный Chrome у заказчика; старую версию не объявлять рекомендуемой для повседневной безопасности.

При запуске проверить localStorage. При недоступности показать причину и не изображать успешное сохранение. Поведение file: зависит от браузера; перенос файлов не гарантирует перенос данных, для него служит JSON. При ошибке записи, включая переполнение, оставлять прежний набор, сохранять введенный текст в форме, показывать ошибку и предлагать копию. Поврежденное хранилище не сбрасывать на демо: доступен экран восстановления и скачивание исходного текста.

Демо создается только при отсутствии набора; сброс — руководителем/администратором после подтверждения и предложения копии. Ежедневной очистки нет. Поддерживается один сеанс редактирования в одной вкладке; предупреждение о второй — Should. Гарантированная многовкладочная синхронизация и объединение правок не требуются.

Пользовательский текст не исполняется как HTML или формулы. Никаких внешних аналитических/сетевых запросов и реальных секретов. Права проверяются и интерфейсом, и штатными обработчиками; владелец локальных файлов все равно может прочитать данные — это не серверная защита.

Для 380 клиентов и 5700 задач за квартал ориентир: открытие до 3 секунд, обычный фильтр до 500 мс на офисном компьютере. Пагинация или виртуализация — выбор разработчика; счетчики/поиск/экспорт всегда по полному набору. Проверить 1366×768 и 1920×1080, масштаб 100% и 125%; характеристики среды и результаты указать в протоколе.

В «О прототипе» обязательна короткая пользовательская справка: роли и вход; добавление клиента/назначений; сроки и календарь; быстрая смена статуса; фактические даты; ожидание документов; разница просрочки сдачи и ожидания приема; снятие/восстановление; CSV/Excel/JSON; тестовая дата; ограничения localStorage и отсутствие настоящего MAX. Примеры — простым языком, без необходимости читать ТЗ.

| К3 | Передача/снятие, история, нагрузка, CSV/XLSX/JSON, справка, исправленные дефекты | Менеджер проверяет, руководитель утверждает |

Это три содержательных этапа, не микрошаги. Блокирующие дефекты предыдущего исправляются до перехода дальше. Сроки, цена, договорные сроки исправлений и гарантийный период не согласованы: фиксируются отдельно до привлечения платного исполнителя, не выдумываются нейросетью. Рекомендуемая обратная связь — в течение 3 рабочих дней после показа, это предложение процесса, не уже заключенное обязательство.

### Протокол и дефекты

Разработчик передает Markdown-протокол самопроверки; менеджер дополняет бизнес-проверки, руководитель отмечает итоговое решение. Протокол — отдельный документ приемки, не четвертый файл страницы. Шаблон:

```text
Версия продукта / дата / этап К1–К3
Проверяли: разработчик, менеджер, руководитель
Среда: Windows, полная версия Chrome, разрешение/масштаб, компьютер
Набор: эталонное демо/тестовая копия; effectiveToday; версия JSON
UC | шаги/вход | ожидание | факт | PASS/FAIL/NOT RUN | доказательство/дефект
Дефект: ID | серьезность | воспроизведение | ожидание/факт | ответственный | состояние
Should: что отсутствует и согласовано ли отсутствие
Итог: принято/исправить; ФИО, дата решения
```

Потеря данных, доступ к чужим задачам сотрудником, ошибочный срок/статус/метрика и неработающий Must блокируют приемку. Исправления повторно проверяются. Мелкие визуальные дефекты устраняются до поставки или явно принимаются руководителем. XLSX проверить открытием в Excel или независимым OOXML-читателем, JSON — восстановлением в тестовой копии. Гарантийные обязательства и сроки не возникают из ТЗ автоматически, устанавливаются договором.

## 21. Будущие потребности — не реализовывать сейчас

Только перечень для отдельного задания: общее хранилище, настоящий вход, синхронизация; MAX за два дня; временное замещение по выбранным клиентам с датами и контролируемым возвратом; политика удаления истории; импорт JSON v2 на сервер.

Не создавать backend, API, бота, серверный планировщик, учетные записи сервисов и секреты на основании этого перечня. Поставщик и бюджет не выбираются за заказчика.

До работы с реальными ПДн компания определяет правовые основания, круг доступа, документы, сроки хранения и согласия там, где именно согласие применимо; оно не является универсальным единственным основанием. Имена/почты сотрудников и данные ИП могут быть персональными данными. Для будущего размещения исходить из хранения баз ПДн граждан РФ в РФ, с оценкой применимых требований и исключений ответственным за ПДн. Это не разрешение выбрать произвольный зарубежный сервис. Поставляемый прототип содержит вымышленные данные, без передачи наружу.

## Приложение А: данные и рекомендации разработчику

Обязателен переносимый JSON с schemaVersion и устойчивыми ID. Новый формат имеет schemaVersion=2. Формат v1 не преобразовывать молча; несовместимый файл отклонить, исходный оставить пользователю. JSON v2 является входом будущей миграции, но не обещает работу с пока несуществующим API.

Сроки/фактические даты — календарные строки, timestamps — UTC. ID не зависят от имени/индекса. taskKey не меняется при переносе срока. Снимок закрытия включает срок, фактические даты и исполнителя.

Отделение хранения, прав, календаря, задач, экспорта и UI внутри app.js рекомендуется, но не является предметом приемки. Разреженные overrides, единый объект хранилища и revision допустимы как оптимизации. terminalKeys, протоколы транзакций вкладок и автоматические миграции сейчас не нужны.

Будущая миграция: выгрузить JSON v2, проверить ссылки и количества; связать userId с настоящими аккаунтами по подтвержденной почте; импортировать календарь/назначения/состояния/историю; сверить контрольные итоги; сохранить исходную копию и отчет. Конфликты ID/почт разрешаются явно. Сейчас реализуется экспорт, не серверный загрузчик.

### Детерминированные правила генерации

1. baseDate фиксируется при первом создании демо равной effectiveToday. Есть команда руководителя «Загрузить эталонное демо 13.10.2026» с подтверждением замены и предложением копии: baseDate/testToday=2026-10-13. Последующая смена тестовой даты не перестраивает демо.
2. Клиенты i=1..380: id=cNNN, имя «Демо Компания NNN»; 1..375 active, 376..380 removed. СНО циклически [ОСНО, УСН доходы, УСН доходы-расходы, Патент]. СНО здесь не назначает обязательства и не означает корректную налоговую комбинацию.
3. Для активных назначить t01,t05,t08,t11; при четном i добавить t02,t06; при i mod 3=0 — t03,t04; при i mod 5=0 — t07,t09,t10. Если дополнительных повторов больше 15 в квартале, не добавлять очередной дополнительный шаблон. Предельные 5700 задач отдельно создаются нагрузочным тестом.
4. Ответственный: активные employee нужной должности по id; взять элемент (i−1) mod длина списка. assignmentId=a_clientId_templateId. Начальный месяц демо — baseDate минус два месяца; новые клиентские записи через UI начинают с текущего месяца.
5. Для текущего и двух предыдущих месяцев задачи сортируются по taskKey; порядковый номер k выбирает цикл из 6 состояний: pending; pending+ждем документов; отчет submitted/платеж sent; отчет accepted/платеж sent; pending; отчет submitted/платеж pending. Даты сдачи/отправки = min(dueDate,baseDate); принятия = min(submittedDate+1 день,baseDate). Снимки и аудит согласованы с состоянием.
6. Для снятых клиентов сохранить по одной отмененной записи с причиной, не создавать рабочие задачи.
7. c001 дополнительно получает t12 со статусом pending. В эталонном демо срок 2026-10-15. Тестовый календарь: 25 и 26 октября 2026 — нерабочие, 27-е рабочее. Подпись «Тестовые исключения, не официальный календарь» обязательна. При включенном переносе РСВ октября имеет срок 27.10.2026.
8. Остальные годы демо — помеченная тестовая пятидневка; готовое демо не перегенерируется при каждом запуске.

Массивы/таблицы/формулы входят в app.js. Отдельный JSON не нужен, сочинять 380 имен компаний и тысячи задач вручную не требуется.

### Отличия от concept.md

Все актуальные правила полностью приведены в этом ТЗ; концепция остается первоначальным документом, не дополнительным источником требований.

| Область | Актуальное правило |
| --- | --- |
| Поставка | Только локальный прототип, без серверной реализации |
| Роли/должности | Три роли; четыре должности отдельно от прав |
| Сотрудник | Свои задачи/клиенты; статус, фактические даты, отметка и комментарий; без редактирования справочников |
| Таблица | Одна строка клиента, сотрудник сверху, без подстрок ответственных |
| Отчет | Закрывает Принято; сдача и ожидание приема отдельны |
| Платеж | Закрывает отправку информации, не оплату |
| Ожидание документов | Независимая отметка |
| Сроки | Общие правила/календарь/исключения, клиентских дат нет; все открытые пересчитываются |
| Клиент | Генерация с текущего месяца, снятие/восстановление без ручных дат обслуживания |
| Передача | По выбранным клиентам, закрытый исполнитель сохраняется |
| Выполнение | Быстрый статус, фактические даты отдельно от аудита; проценты по закрытым за период, прошлые долги отдельно |

| Данные | 20 пользователей/380 клиентов, детерминированная фикстура, СНО как справочная метка |
